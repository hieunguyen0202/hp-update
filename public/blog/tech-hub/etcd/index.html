    etcd: backup, restore & APISIX as config store

    etcd là “bộ nhớ dài hạn” của Kubernetes — và cũng là nơi Apache APISIX giữ routes, upstreams, plugins. Bài này gom lại những gì tài liệu chính thức và các runbook production hay nhắc: snapshot đúng cách, verify, restore control plane, rồi nhìn etcd dưới góc gateway.

    Level: Platform / SRE Stack: Kubernetes · etcd · APISIX Updated: 2026-08

    Tại sao etcd quan trọng?

    Theo Kubernetes docs, etcd là consistent, highly-available key-value store dùng làm backing store cho toàn bộ cluster data. Mất etcd trên mọi control-plane node gần như đồng nghĩa với mất desired state: Pods, Services, Secrets, ConfigMaps, CRDs, RBAC…

    Hai hệ quả vận hành bạn cần nhớ:

    • Backup không chỉ là “có file” — phải lấy được snapshot khi API đã chết (off-cluster / NFS / object storage độc lập).
    • Restore không phải copy file vào chỗ cũ — phải dừng API server, dựng lại member nhất quán, rồi mới mở lại control plane.

    etcdctl vs etcdutl

    Từ etcd 3.5 trở đi, vai trò được tách rõ hơn (Kubernetes cũng khuyến nghị tương tự):

    • etcdctl — client mạng: health, member list, snapshot save từ member đang chạy.
    • etcdutl — thao tác trên file dữ liệu: snapshot status, snapshot restore, defrag offline…

    etcdctl snapshot status|restore đã deprecated; hãy quen với etcdutl trước khi etcd 3.6 gỡ hẳn.

    Backup: lấy snapshot đúng cách

    1) Live snapshot bằng etcdctl

    Snapshot từ một member đang sống không làm chậm đáng kể member đó (theo docs Kubernetes). Trên kubeadm, endpoint + cert thường nằm trong static Pod etcd: 

    export ETCDCTL_API=3
export ENDPOINT=https://127.0.0.1:2379

etcdctl --endpoints="$ENDPOINT" \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save /var/backups/etcd/snapshot-$(date +%Y%m%d-%H%M%S).db

    2) Verify trước khi tin

    etcdutl --write-out=table snapshot status /var/backups/etcd/snapshot-….db

    Bạn cần thấy hash, revision, total keys, size. Snapshot “im lặng thành công” nhưng size ~0 hoặc status lỗi = chưa phải backup.

    3) Tần suất & nơi lưu

    • RPO: nhiều team chọn 1–6 giờ tùy tốc độ thay đổi cluster. Cluster deploy dày → snapshot dày hơn.
    • Off-site: đẩy sang S3 / GCS / NFS ngoài cluster. Backup chỉ reachable qua API đang chết thì không phải backup.
    • Bảo mật: snapshot chứa Secrets — mã hóa at-rest, permission 0600, hạn chế ai pull được.
    • Thời điểm: tránh peak I/O; backup trước/sau upgrade control plane; với OpenShift, tránh snapshot trong cửa sổ xoay cert 24h đầu (theo guidance Red Hat).

    Volume snapshot (EBS/CSI) là lớp bổ sung, không thay thế snapshot logic của etcd nếu bạn cần restore có kiểm soát revision / membership.

    Restore control plane

    Caution (Kubernetes): nếu API server còn chạy, đừng restore etcd “xen vào”. Quy trình chuẩn: stop mọi API server → restore etcd → start lại API server. Nên restart thêm scheduler, controller-manager, kubelet để tránh stale cache.

    Single-member / lab (kubeadm stacked)

    1. Dừng kube-apiserver (và etcd) trên control plane — thường bằng cách move/rename manifest trong /etc/kubernetes/manifests.
    2. Restore vào data-dir mới (đừng ghi đè DB đang bị process giữ):
    etcdutl --data-dir=/var/lib/etcd-restore snapshot restore snapshot.db
    1. Trỏ volume etcd-data trong manifest etcd sang thư mục vừa restore (hoặc thay thế /var/lib/etcd một cách có kiểm soát sau khi process đã dừng).
    2. Đưa manifest trở lại, đợi static Pod healthy, kiểm tra kubectl get nodes / objects trước snapshot quay lại.

    Mẹo hay gặp trên lab: chỉ đổi --data-dir bên trong container mà quên retarget hostPath → etcd lên với DB rỗng, trông như “restore thất bại bí ẩn”.

    HA restore (3/5 members)

    Các runbook production (và etcd disaster recovery) hội tụ quanh một pattern:

    1. Restore snapshot một lần trên member đầu, coi như single-member cluster mới.
    2. etcdctl member add từng node còn lại; joiner dùng --initial-cluster-state=existing và --initial-cluster khớp membership.
    3. Chờ member mới healthy / catch-up trước khi add tiếp — tránh mất quorum giữa chừng.
    4. Khi rewind revision, dùng cặp flag restore hiện đại (etcd gần đây): --bump-revision + --mark-compacted để buộc informer re-list, tránh controller sống với cache “tương lai”.

    --initial-cluster-token nên set tường minh khi bootstrap lại (etcd 3.6 siết hơn về việc này) để tránh hai cụm “gặp nhau” nhầm.

    Những gì không nằm trong snapshot

    Snapshot etcd khôi phục API state. Nó không mang theo:

    • Dữ liệu PersistentVolume / disk workload
    • Image trên node / registry
    • DNS ngoài cluster, load balancer cloud, IAM…

    DR plan phải tách lớp: etcd (control plane) + Velero/CSI (apps & volumes) + infra-as-code (cloud resources).

    etcd trong Apache APISIX

    APISIX không lưu routes trên từng data plane node theo kiểu file tĩnh một chiều. Trong mô hình traditional, config_provider: etcd — mọi runtime config (routes, upstreams, consumers, SSL, plugin metadata) nằm dưới một prefix (mặc định /apisix). Các instance APISIX watch etcd và cập nhật routing động khi Admin API / Dashboard ghi thay đổi.

    Cấu hình tối thiểu

    deployment:
  role: traditional
  role_traditional:
    config_provider: etcd
  etcd:
    host:
      - "https://etcd-0.etcd:2379"
      - "https://etcd-1.etcd:2379"
      - "https://etcd-2.etcd:2379"
    prefix: "/apisix"
    timeout: 30
    • Production: Helm chart khuyến nghị tắt built-in Bitnami etcd (dev/test) và nối external etcd do bạn vận hành.
    • Multi-tenant config: nhiều cụm APISIX có thể chia một etcd nếu dùng prefix khác nhau.
    • mTLS: cấu hình deployment.etcd.tls.cert/key (+ CA tin cậy) khi etcd bắt buộc client cert — xem APISIX mTLS docs.

    Backup APISIX = backup prefix etcd

    Mất etcd của APISIX = mất toàn bộ control-plane config gateway (routes/upstreams), dù data plane process vẫn có thể còn cache tạm. Thực tế:

    • Snapshot cả cụm etcd (giống K8s), hoặc
    • Export định kỳ qua Admin API / GitOps nguồn sự thật (IaC) — snapshot vẫn là lớp DR cuối.

    Đừng nhầm hai cụm etcd: etcd của Kubernetes và etcd của APISIX thường là hai lifecycle riêng. Backup một cái không cứu được cái kia.

    Checklist mang đi làm

    • ☐ Có snapshot tự động + verify (etcdutl snapshot status)
    • ☐ Có ít nhất một đường lấy backup không phụ thuộc API cluster
    • ☐ Snapshot được mã hóa / ACL chặt
    • ☐ Đã diễn tập restore trên lab (single rồi mới HA)
    • ☐ Biết dừng API server trước khi restore
    • ☐ APISIX: etcd external + mTLS + prefix rõ ràng + backup riêng
    • ☐ DR phủ cả PV / registry / DNS — không chỉ etcd
