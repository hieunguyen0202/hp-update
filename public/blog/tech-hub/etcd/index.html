    Sơ đồ trực quan — etcd cluster (kOps + etcd-manager)

    Tab dưới đây tóm tắt nội dung canvas phân tích: Raft quorum, kiến trúc kOps (main + events), control loop, backup S3, sự cố trashcan, và luồng restore-backup qua S3 command queue.

    Raft write path — 3 member (quorum = 2)

    kube-apiserver ──write──► etcd Leader (master-1)
                                │
                   AppendEntries ├──► Follower (master-2)
                                └──► Follower (master-3)
                                │
                   commit khi ≥ 2/3 ACK (quorum)

    Mất 1 node → cluster vẫn hoạt động. Mất 2 node → mất quorum → API không nhận write mới.

    3 masters chịu 1 failure. Không chạy 2 member (quorum=2, mất 1 là chết).

    3 master HA — 2 etcd cluster = 6 EBS volumes

    master-1              master-2              master-3
├─ kube-apiserver     ├─ kube-apiserver     ├─ kube-apiserver
├─ etcd-mgr-main      ├─ etcd-mgr-main      ├─ etcd-mgr-main
│  └─ etcd (Raft)     │  └─ etcd            │  └─ etcd
│  └─ EBS: main       │  └─ EBS: main       │  └─ EBS: main
├─ etcd-mgr-events    ├─ etcd-mgr-events    ├─ etcd-mgr-events
   └─ EBS: events        └─ EBS: events        └─ EBS: events

    etcd-manager mount EBS, spawn etcd child process. Tách main (object K8s) và events (Events churn cao). Xem kOps boot sequence.

    etcd-manager Leader control loop

    1. Gossip + elect weak leader (member ID thấp nhất)
    2. Query peers: ai đang host etcd process?
    3. Start / add / remove member (qua Raft)
    4. Đọc lệnh từ S3 work queue (restore-backup…)
    5. Periodic backup → S3

    Source: etcd-manager README — chạy ngoài vòng phụ thuộc Kubernetes API.

    Backup pipeline → S3

    etcd Leader ──snapshot──► gzip ──► S3
                                    ├─ etcd.backup.gz
                                    └─ _etcd_backup.meta (etcdVersion, clusterSpec)

s3://<cluster>/backups/etcd/main/
  control/                    ← spec + command queue
  2024-05-07T18:28:01Z-000977/
    etcd.backup.gz
    _etcd_backup.meta

    Trigger: định kỳ + trước mọi cluster modification. Format: backup structure.

    Sự cố trashcan — pattern production

    • Bình thường Leader backup định kỳ; 3 member Raft healthy.
    • Trigger kOps upgrade / restart etcd-manager / mất etcd-cluster-spec trên S3.
    • etcd-manager Thấy “no cluster” → seed cluster MỚI; move datadir cũ → *-trashcan.
    • Hậu quả Cluster etcd mới = EMPTY → API mất K8s state.
    • Cứu cánh Backup S3 gần nhất hoặc salvage từ trashcan → restore queue.
    TRƯỚC:  /mnt/etcd-main/member/     (Raft data)
SAU:    member/ (EMPTY)  +  member-trashcan/ (data cũ)
    Runbook thực tế: kops#16416 — trashcan recovery. Trashcan là plain copy, không phải snapshot chuẩn — cần convert nếu upload manual lên S3.

    restore-backup → S3 command queue (không gọi thẳng etcd)

    Admin (etcd-manager-ctl restore-backup)
        │
        ▼ ghi file
S3: control/<ts>-000000/_command.json
        │
        ▼ restart etcd-manager trên ALL masters
Leader đọc queue → cluster MỚI → restore etcd.backup.gz
        │
        ▼
kube-apiserver reconnect (data từ backup timestamp)

    restore-backup chỉ enqueue lệnh — phải restart etcd-manager để pick up. Restore cả main và events riêng. Chi tiết: Level 5.5.

    Level 1 — Mental model (đọc trước khi chạy lệnh)

    etcd là distributed key-value store dùng Raft consensus. Mọi write phải được leader replicate và commit khi đạt quorum (đa số members). Đó là lý do etcd “chậm mà chắc” — phù hợp lưu state quan trọng (Kubernetes API objects), không phải cache throughput cao.

    Bảng quorum (nhớ lòng)

    MembersQuorum cầnChịu được mấtGhi chú production
    110Chỉ lab / test
    321HA tối thiểu (kubeadm HA phổ biến)
    532K8s docs khuyến nghị production lớn
    743Hiếm; trade-off latency vs fault tolerance

    Công thức: cluster N members chịu tối đa (N-1)/2 member chết vĩnh viễn. Mất quorum → cluster read-only hoặc không phục vụ write → scheduler không schedule Pod mới, dù workload cũ có thể vẫn chạy.

    Luồng write (Raft — đơn giản hóa)

    Client (apiserver) ──write──► Leader etcd
                                  │
                    replicate log ├──► Follower 1
                                  ├──► Follower 2
                                  │
                     commit khi ≥ quorum ACK
                                  │
                     trả success cho client

    Thuật ngữ hay gặp

    • Revision — số phiên bản global của keyspace; snapshot ghi lại revision tại thời điểm backup.
    • MVCC — etcd giữ lịch sử revision; DB phình theo thời gian → cần compaction + defrag.
    • Client URL (:2379) — apiserver / etcdctl nói chuyện ở đây.
    • Peer URL (:2380) — replication Raft giữa members.
    • Stacked etcd — etcd chạy cùng control-plane node (static Pod kubeadm).
    • External etcd — cụm etcd tách riêng; kubeadm trỏ --etcd-servers vào đó.

    Production baseline (Kubernetes docs): etcd 3.4.29+ hoặc 3.5.11+; số members lẻ; disk I/O và network ổn định; không autoscale etcd như worker node.

    Level 3 — Hands-on hàng ngày

    3.1 Alias etcdctl trên kubeadm (copy-paste)

    SSH vào control-plane node (hoặc crictl exec vào container etcd):

    export ETCDCTL_API=3
export ENDPOINT=https://127.0.0.1:2379
export CACERT=/etc/kubernetes/pki/etcd/ca.crt
export CERT=/etc/kubernetes/pki/etcd/server.crt
export KEY=/etc/kubernetes/pki/etcd/server.key

alias etcdctl='etcdctl --endpoints="$ENDPOINT" --cacert="$CACERT" --cert="$CERT" --key="$KEY"'

    3.2 Health & membership

    # Member + role (leader có IS LEADER)
etcdctl member list -w table

# Health từng endpoint
etcdctl endpoint health -w table

# Chi tiết: DB size, leader, raft index…
etcdctl endpoint status -w table

# Alarm (NOSPACE = đầy quota → cluster read-only)
etcdctl alarm list

    Output endpoint health mong đợi: mỗi endpoint healthy: true. Nếu một member unhealthy nhưng quorum còn → replace member sớm (Level 6).

    3.3 Đọc key Kubernetes (chỉ khi troubleshoot)

    Prefix phổ biến: /registry/. Luôn dùng --prefix + limit:

    # Đếm keys dưới /registry/pods (cẩn thận cluster lớn)
etcdctl get /registry/pods --prefix --keys-only | head

# Một key cụ thể (ví dụ sau khi biết path từ audit)
etcdctl get /registry/namespaces/default -w json | jq .

    Lưu ý: thao tác trực tiếp trên etcd có thể phá consistency với apiserver. Ưu tiên kubectl; chỉ dùng etcdctl khi API không phản hồi hoặc forensic.

    3.4 kOps — vào etcd qua etcd-manager pod

    Theo kOps etcd administration:

    # Xem version etcd trong cluster spec
kops get cluster --full -o yaml | grep -A5 etcdCluster

CONTAINER=$(kubectl get pods -n kube-system \
  | grep etcd-manager-main | head -1 | awk '{print $1}')
kubectl exec -it -n kube-system "$CONTAINER" -- sh

# Trong pod (version khớp cluster, port kOps thường 4001):
ETCD_VERSION=3.5.13
ETCDDIR=/opt/etcd-v$ETCD_VERSION
CERTDIR=/rootfs/srv/kubernetes/kube-apiserver/
alias etcdctl="ETCDCTL_API=3 $ETCDDIR/etcdctl \
  --cacert=$CERTDIR/etcd-ca.crt \
  --cert=$CERTDIR/etcd-client.crt \
  --key=$CERTDIR/etcd-client.key \
  --endpoints=https://127.0.0.1:4001"

    Level 4 — Bảo mật & authentication

    Kubernetes docs (quan trọng): “Access to etcd is equivalent to root permission in the cluster.” Và: “etcd authentication is not planned for Kubernetes.” — tức K8s dùng TLS client certificate, không dùng user/password etcd RBAC cho apiserver.

    4.1 Hai lớp TLS

    LớpPortCert thường gặpFlags etcd
    Client ↔ etcd 2379 (kOps: 4001) server.crt / apiserver client cert --cert-file, --key-file, --client-cert-auth
    Peer ↔ peer 2380 peer.crt --peer-cert-file, --peer-client-cert-auth

    mTLS peer: mỗi member verify cert của member kia — chống node giả tham gia Raft. Client cert auth: chỉ client có cert ký bởi CA tin cậy mới gọi được API etcd.

    4.2 kubeadm — ai được nói chuyện với etcd?

    kube-apiserver mount flags:

    --etcd-certfile=/etc/kubernetes/pki/apiserver-etcd-client.crt
--etcd-keyfile=/etc/kubernetes/pki/apiserver-etcd-client.key
--etcd-cafile=/etc/kubernetes/pki/etcd/ca.crt
--etcd-servers=https://127.0.0.1:2379,...

    Thực hành production:

    • Firewall: chỉ CP nodes + break-glass bastion tới 2379/2380.
    • Không expose etcd ra Internet; không mở NodePort “tạm debug”.
    • Theo dõi expiry cert etcd — kubeadm có kubeadm certs check-expiration.
    • Bật encryption at rest trên apiserver (Secrets trong etcd được mã hóa thêm lớp).

    4.3 etcd RBAC (khi etcd không phải K8s — ví dụ APISIX)

    etcd hỗ trợ user/password + role (read/write trên prefix). APISIX production thường dùng TLS + cert hoặc RBAC nếu bật --auth-token. Tách biệt hoàn toàn với Kubernetes RBAC. 

    # Ví dụ standalone etcd (lab) — KHÔNG dùng pattern này cho K8s control plane
etcdctl user add apisix --new-user-password='***'
etcdctl role add apisix-role
etcdctl role grant-permission apisix-role readwrite /apisix
etcdctl user grant-role apisix apisix-role
etcdctl auth enable

    Level 5 — Backup & restore (DR)

    5.0 etcdctl vs etcdutl

    • etcdctl snapshot save — chụp từ member đang chạy (qua mạng).
    • etcdutl snapshot status — verify file backup.
    • etcdutl snapshot restore — dựng data-dir mới từ file (offline).

    5.1 Live snapshot (kubeadm)

    etcdctl snapshot save "/var/backups/etcd/snapshot-$(date +%Y%m%d-%H%M%S).db"

etcdutl --write-out=table snapshot status /var/backups/etcd/snapshot-*.db
# Kiểm tra: HASH, REVISION, TOTAL KEYS, TOTAL SIZE > 0

    5.2 Off-site & RPO

    • Đẩy snapshot ra S3/GCS/NFS ngoài cluster — DR khi API chết vẫn lấy được file.
    • RPO 1h–6h tùy tần suất deploy; CronJob + systemd timer đều được.
    • Encrypt snapshot (chứa toàn bộ Secrets).
    • Backup trước và sau upgrade etcd / control plane.

    5.3 Restore single-member (lab kubeadm)

    Caution: stop tất cả kube-apiserver trước khi restore.

    1. Move manifest kube-apiserver.yaml và etcd.yaml ra khỏi /etc/kubernetes/manifests/.
    2. Restore vào thư mục mới:
    etcdutl --data-dir=/var/lib/etcd-restored snapshot restore snapshot.db
    1. Sửa hostPath volume etcd-data → /var/lib/etcd-restored.
    2. Đưa manifest lại; verify kubectl get nodes.

    Pitfall: đổi --data-dir trong container nhưng quên hostPath → etcd lên DB trống.

    5.4 Restore HA (3/5 members)

    1. Stop API server trên mọi master.
    2. Restore snapshot một lần trên master1 → single-member cluster.
    3. etcdctl member add master2, master3 — từng cái một; joiner: ETCD_INITIAL_CLUSTER_STATE=existing.
    4. Chờ member healthy trước khi add tiếp (tránh reject khi chưa catch-up).
    5. Restore với revision rewind: dùng --bump-revision + --mark-compacted (etcd mới) để controller/informer không giữ cache stale.
    6. Start lại apiserver, scheduler, controller-manager; cân nhắc rolling restart kubelet.

    5.5 Restore trên kOps (etcd-manager-ctl + S3 queue)

    Theo kOps backup/restore docs:

    • Backup main và events nằm trên S3 cùng cluster state.
    • Dùng etcd-manager-ctl (binary từ etcd-manager releases) — không cần chạy trong cluster nếu có quyền S3.
    • Restore là lệnh async qua S3 — không gọi thẳng etcd, không restart ngay khi gõ lệnh.
    • Tạo etcd cluster mới rồi restore backup lên — data sau backup timestamp bị mất.

    5.5.1 restore-backup ghi gì lên S3?

    etcd-manager-ctl restore-backup <timestamp> không SSH vào master. Nó đọc control/etcd-cluster-spec, rồi ghi file lệnh: 

    s3://<bucket>/<cluster>/backups/etcd/main/control/
  2024-05-07T18:30:00Z-000000/
    _command.json    ← restore_backup: { backup, cluster_spec }

    Leader etcd-manager đọc _command.json trong control loop (sau khi bạn restart manager trên tất cả master). Xem source pkg/commands/vfs.go.

    5.5.2 Các bước restore (timeline)

    BướcLệnh / hành động
    1list-backups cho main và events
    2restore-backup <timestamp> — enqueue vào S3 (chưa restore)
    3list-commands — verify lệnh trong queue
    4crictl stop etcd-manager trên cả 3 master
    5Leader pick up → cluster mới + restore etcd.backup.gz
    6apiserver up; follow-up: restart kubelet nếu pod không start
     
    # Liệt kê backup
etcd-manager-ctl --backup-store=s3://BUCKET/CLUSTER/backups/etcd/main list-backups
etcd-manager-ctl --backup-store=s3://BUCKET/CLUSTER/backups/etcd/events list-backups

# Enqueue restore (main + events — timestamp khác nhau)
etcd-manager-ctl --backup-store=s3://BUCKET/CLUSTER/backups/etcd/main \
  restore-backup 2024-05-07T18:28:01Z-000977
etcd-manager-ctl --backup-store=s3://BUCKET/CLUSTER/backups/etcd/events \
  restore-backup 2024-05-07T18:28:05Z-000012

# Verify queue
etcd-manager-ctl --backup-store=s3://BUCKET/CLUSTER/backups/etcd/main list-commands

# Trigger restore — trên mỗi master
crictl ps | grep etcd-manager
crictl stop <container-id>

    Plan B (trashcan): scp *-trashcan → etcdctl snapshot restore --skip-hash-check → upload manual backup lên S3 → restore-backup. Tham khảo kops#16416 và HA kOps etcd recovery (Medium).

    Sau restore: apiserver có thể chậm (reconcile state) — restore troubleshooting.

    Level 6 — Multi-member: add / remove / replace

    Flow chuẩn khi member1 chết (theo Kubernetes docs):

    # 1) List members (từ endpoint còn sống)
etcdctl --endpoints=https://10.0.0.2:2379,https://10.0.0.3:2379 member list

# 2) Stop etcd trên node hỏng; stop traffic ghi vào node đó

# 3) Remove member cũ
etcdctl member remove <MEMBER_ID>

# 4) Add member mới
etcdctl member add member4 --peer-urls=https://10.0.0.4:2380

# 5) Trên node mới — QUAN TRỌNG: state=existing
export ETCD_NAME="member4"
export ETCD_INITIAL_CLUSTER="member2=https://10.0.0.2:2380,member3=https://10.0.0.3:2380,member4=https://10.0.0.4:2380"
export ETCD_INITIAL_CLUSTER_STATE=existing
# start etcd với cert/flags đúng

# 6) Cập nhật --etcd-servers trên apiserver nếu cần; restart apiserver

    Lỗi kinh điển: joiner thiếu --initial-cluster-state=existing → etcd bootstrap cluster mới → cluster ID mismatch.

    Scaling: K8s khuyến nghị không scale etcd linh hoạt; nếu cần, 3→5 members theo runtime reconfiguration — một member một lần.

    Level 7 — kOps + etcd-manager (hiểu sâu)

    etcd-manager tồn tại vì vòng phụ thuộc: Kubernetes cần etcd, nhưng etcd-operator kiểu chạy trong K8s lại cần API đã sẵn. kOps chạy etcd-manager như static Pod / systemd trên master, ngoài vòng đời Deployment thông thường.

    Vòng lặp điều khiển (tóm tắt từ source etcd-manager)

    Mỗi master chạy etcd-manager controller
        │
        ▼
Gossip discovery + elect "weak leader" (ID thấp nhất)
        │
        ▼
Leader loop:
  • Peer nào đang host etcd?
  • Chưa có cluster → bootstrap quorum trên subset peers
  • Thiếu member → member add (qua Raft)
  • Thừa / unhealthy member → member remove
  • Đọc lệnh từ S3 work queue (restore…)
  • Periodic backup → S3
        │
        ▼
Mount EBS volume (tag) → chạy etcd child process trên node đó

    HA 3 master → thường 6 volumes. etcd-manager đảm bảo volume gắn đúng node và process etcd sống — bạn không ssh vào từng member để member add thủ công như kubeadm.

    Sự cố: etcd-manager seed cluster mới + trashcan

    Khi mất file control trên S3 (etcd-cluster-spec, etcd-cluster-created) hoặc etcd-manager restart sau upgrade, leader có thể coi cluster chưa tồn tại → bootstrap cluster mới rỗng, archive datadir cũ vào *-trashcan trên EBS. etcd-manager không hỏi trước khi làm việc này.

    • Nguyên nhân phổ biến: S3 lifecycle xóa control files — etcd-manager#299.
    • Dấu hiệu: API trống / cluster “mới”; log no cluster spec set - must seed new cluster.
    • Cứu: restore-backup từ S3; hoặc salvage trashcan (kops#16416).
    • Phòng: không lifecycle-delete backups/etcd/*/control/; monitor backup freshness.

    Level 8 — Maintenance, APISIX, troubleshooting

    8.1 Defrag & compaction

    • MVCC làm DB phình → monitor etcd_mvcc_db_total_size_in_bytes.
    • etcdctl defrag — tốn I/O; chạy theo lịch (CronJob / etcd-defrag).
    • Alarm NOSPACE → cluster từ chối write → defrag + tăng quota hoặc compaction.
    etcdctl defrag --endpoints=https://127.0.0.1:2379
etcdctl alarm disarm  # sau khi xử lý nguyên nhân đầy disk

    8.2 Upgrade

    Luôn backup trước. Upgrade theo minor etcd docs; patch version thường tương thích restore chéo patch.

    8.3 APISIX — etcd là config store (tách biệt K8s)

    deployment:
  role_traditional:
    config_provider: etcd
  etcd:
    host: ["https://etcd-0:2379", "https://etcd-1:2379"]
    prefix: "/apisix"
    timeout: 30
    tls:
      cert: /path/to/client.pem
      key:  /path/to/client-key.pem

    APISIX watch prefix → cập nhật route realtime. Production: external etcd 3/5 members, mTLS, backup snapshot riêng. Đừng dùng built-in Bitnami etcd của Helm chart cho prod.

    Cheatsheet một trang (in ra dán tủ)

    # === HEALTH ===
etcdctl member list -w table
etcdctl endpoint health -w table
etcdctl endpoint status -w table
etcdctl alarm list

# === BACKUP ===
etcdctl snapshot save /backups/etcd-$(date +%F-%H%M).db
etcdutl --write-out=table snapshot status /backups/etcd-*.db

# === RESTORE (offline — stop apiserver first) ===
etcdutl --data-dir=/var/lib/etcd-new snapshot restore snapshot.db
# retarget hostPath etcd-data → /var/lib/etcd-new

# === MEMBER REPLACE ===
etcdctl member remove <id>
etcdctl member add NAME --peer-urls=https://IP:2380
# join: ETCD_INITIAL_CLUSTER_STATE=existing

# === MAINTENANCE ===
etcdctl defrag --endpoints=...
etcdctl alarm disarm

# === KOPS ===
etcd-manager-ctl --backup-store=s3://... list-backups
# restore → restart etcd-manager pods on all masters

    Checklist production

    • ☐ 3 hoặc 5 members, không autoscale
    • ☐ Snapshot tự động + verify + off-site + encrypt
    • ☐ Đường lấy backup khi API chết
    • ☐ Diễn tập restore (lab → staging)
    • ☐ Monitor disk, defrag định kỳ, alert NOSPACE
    • ☐ Cert rotation có kế hoạch
    • ☐ Biết pattern của cluster: kubeadm vs kOps vs managed
    • ☐ APISIX/etcd gateway: cụm riêng, backup riêng
